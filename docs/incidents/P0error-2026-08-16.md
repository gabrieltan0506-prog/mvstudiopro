## 一、事故結論 / 1. Incident Conclusion

本次事故的直接原因，是未經用戶授權，把 `20,000` 從展示或保護口徑錯誤地實現成小紅書真實 current 數據的硬上限。小紅書原有 591,066 條 current 數據因此在生產文件中被裁成約 20,000 條。

The direct cause was an unauthorized change that implemented `20,000` as a hard cap on the real Xiaohongshu current dataset rather than as a display or protection threshold. As a result, the production current store was truncated from 591,066 records to approximately 20,000.

這不是單純的頁面顯示錯誤，而是生產 TrendStore 真實數據文件被重寫。GitHub 完整冷備份避免了不可逆損失，但不能減輕該變更本身的嚴重性。

This was not merely a UI display defect. The real production TrendStore files were rewritten. The complete GitHub cold backup prevented irreversible loss, but that does not reduce the severity of the change.

該事故同時屬於：

- 未授權的數據語義變更；
- 生產數據破壞；
- 部署校驗被錯誤放寬後掩蓋回退；
- 恢復流程未先隔離後臺寫入；
- 對用戶作出結論前沒有完成真實狀態核驗。

This incident simultaneously involved:

- an unauthorized change to data semantics;
- destructive modification of production data;
- masking of regression by an incorrectly relaxed deployment guard;
- a recovery process that did not isolate background writers first;
- conclusions communicated before the real production state was verified.

## 二、用戶未被告知和未授權的內容 / 2. What Was Not Explained or Authorized

施工前本應明確向用戶說明：

1. `20,000` 究竟是頁面展示數量、最低保護值，還是會真實刪除 current 數據的存儲上限；
2. 小紅書多數記錄缺少 `publishedAt`，會全部進入 undated 分支；
3. 新邏輯可能把約 571,066 條已有數據從 current 移除；
4. 對收費趨勢報告、分析窗口、歷史與實時口徑、部署回退保護的影響；
5. 完整備份、回滾和真實數據演練結果；
6. 得到用戶明確授權後才允許上線。

Before implementation, the user should have been explicitly told:

1. whether `20,000` was a UI display count, a minimum protection value, or a storage cap that would actually remove current records;
2. that most Xiaohongshu records lacked `publishedAt` and would enter the undated branch;
3. that the new logic could remove approximately 571,066 existing records from current;
4. the impact on paid trend reports, analysis windows, historical/live semantics, and deployment regression protection;
5. the complete backup, rollback plan, and real-data rehearsal result;
6. that deployment required explicit user authorization.

以上說明和授權均未在破壞性改動前完成。這是本次事故最嚴重的流程與誠信錯誤。

None of the above explanation or authorization was completed before the destructive change. This was the most serious process and integrity failure in the incident.

## 三、技術根因 / 3. Technical Root Cause

### 3.1 PR #1246 引入真實裁剪 / PR #1246 introduced real truncation

PR #1246（合併提交 `1de70fe1`）在 `server/growth/trendStore.ts` 引入 `MAX_UNDATED_HOT_ITEMS = 20_000`。小紅書大量記錄沒有合法 `publishedAt`，因此 undated 數據被按熱度排序後只保留前 20,000 條。

PR #1246 (merge commit `1de70fe1`) introduced `MAX_UNDATED_HOT_ITEMS = 20_000` in `server/growth/trendStore.ts`. Because a large portion of Xiaohongshu records lacked a valid `publishedAt`, the undated dataset was ranked by hotness and only the first 20,000 records were retained.

這段邏輯把“控制窗口或展示規模”錯誤地變成“破壞真實 current 數據”。

This logic incorrectly converted a window/display-size concern into destructive truncation of the real current store.

### 3.2 PR #1248 掩蓋回退 / PR #1248 masked the regression

PR #1248（合併提交 `769cdb01`）為小紅書增加 `currentRetentionCap: 20000`，使增長單調校驗把 20,000 當成可接受值。原本應該阻止 591,066 → 20,000 回退的部署門禁因此失效。

PR #1248 (merge commit `769cdb01`) added `currentRetentionCap: 20000` for Xiaohongshu, causing the monotonic growth guard to accept 20,000. The deployment gate that should have blocked the 591,066 → 20,000 regression therefore failed.

### 3.3 恢複函數跨平臺讀寫過重 / Recovery function loaded and rewrote too much

PR #1249 初版恢複函數通過完整 `readTrendStore()` 與 `writeStore()` 加載並重寫所有平臺。生產恢復期間後臺 backfill 仍在寫入，導致競爭、SSH EOF、恢復結果被覆蓋，並使抖音 current 一度從 343,222 降至 312,811。

The initial recovery function in PR #1249 used full `readTrendStore()` and `writeStore()` operations that loaded and rewrote every platform. While recovery ran, background backfill continued writing, causing races, SSH EOF responses, overwritten recovery results, and a temporary Douyin current regression from 343,222 to 312,811.

最終生產恢復改用單平臺原子寫入，只更新小紅書的 truth、derived file、manifest 和 current stub，不再重寫其他平臺。

The final production recovery used single-platform atomic writes, updating only Xiaohongshu truth, the derived file, the manifest, and the current stub without rewriting other platforms.

## 五、恢復過程中的錯誤 / 5. Errors During Recovery

### 5.1 首次整包 SFTP 被截斷 / Initial full-file SFTP was truncated

本機文件為 42,723,935 字節，但 Fly 首次只收到 28,016,640 字節，腳本報 `unexpected end of file`。該失敗發生在寫庫前，未形成恢復結果。

The local file was 42,723,935 bytes, but Fly initially received only 28,016,640 bytes. The script failed with `unexpected end of file`. This failure occurred before the database write and produced no recovery result.

### 5.2 分片並行上傳再次失敗 / Parallel chunk uploads also failed

文件雖已分片，但錯誤地並行上傳，多個分片再次被截斷。之後改為 4MB 分片嚴格串行上傳，每片單獨確認成功。

Although the file was split, the chunks were incorrectly uploaded in parallel, and several chunks were truncated again. The process was then changed to strict sequential 4 MB uploads with individual success confirmation.

### 5.3 未先凍結寫入 / Background writes were not isolated first

恢復初期把 `backfill` 誤稱為“採集暫停”。實際上 backfill 仍會運行並寫數據。正確止損是在用戶明確授權後臨時凍結三平臺調度，完成恢復後再解除凍結。

At the beginning of recovery, `backfill` was incorrectly described as “collection paused.” In reality, backfill continued running and writing data. The correct containment action was to temporarily freeze the three platform schedulers after explicit user authorization and release the freeze after recovery.

## 七、仍未關閉的風險 / 7. Remaining Risks

1. PR #1249 的倉庫恢複函數仍會通過完整 `readTrendStore()` / `writeStore()` 讀取和寫入所有平臺；生產事故恢復應改為正式的單平臺原子入口，避免跨平臺競爭與高內存佔用。
2. 系統缺少真正的 `paused` 運行模式；`live` 與 `backfill` 都可能寫入。以後恢復前應有顯式、可審計、自動超時恢復的寫入凍結開關。
3. GitHub Release 的單平臺公開資產存在過期問題：實測 `platform-xiaohongshu.json.gz` 只有 116,335 條，`platform-douyin.json.gz` 只有 156,506 條，而整包 `growth-platforms.tar.gz` 才包含最新完整基線。備份發佈流程必須校驗所有資產同批次、同 manifest。
4. Fly SFTP 大文件上傳會靜默截斷，不能只看命令退出；必須核對大小與 SHA-256，或使用可靠的可續傳協議。
5. 抖音 current 仍低於 GitHub 完整基線，因用戶明確決定本輪不恢復而保留現狀。
6. 尚未完成一次小紅書恢復後的完整新採集輪次驗收；當前只證明恢復後即時未回退。應在下一輪檢查 current 不低於 591,286。

1. The repository recovery function in PR #1249 still reads and writes all platforms through full `readTrendStore()` / `writeStore()` calls. Production incident recovery should use an official single-platform atomic entry point to avoid cross-platform races and high memory use.
2. The system lacks a true `paused` runtime mode; both `live` and `backfill` may write. Future recovery requires an explicit, auditable write freeze with automatic timeout recovery.
3. GitHub Release single-platform assets are stale: `platform-xiaohongshu.json.gz` contained only 116,335 records and `platform-douyin.json.gz` only 156,506, while `growth-platforms.tar.gz` held the latest complete baseline. The backup publishing process must verify all assets belong to the same manifest and batch.
4. Large Fly SFTP uploads can be silently truncated. Exit status alone is insufficient; size and SHA-256 must be verified, or a reliable resumable transfer protocol must be used.
5. Douyin current remains below the complete GitHub baseline because the user explicitly decided not to restore it in this operation.
6. A full post-recovery Xiaohongshu collection cycle has not yet been accepted. Only the absence of an immediate regression has been verified. The next cycle must confirm current remains at or above 591,286.

## 八、強制防復發門禁 / 8. Mandatory Prevention Gates

### 8.1 數據語義與授權 / Data semantics and authorization

- 任何 retention、cap、window、dedupe 或 prune 邏輯，必須明確區分“展示限制”和“真實存儲刪除”。
- 可能降低生產 current 總量的修改，必須在施工前展示真實數據影響並取得用戶明確授權。
- 禁止把容量優化作為隱含授權。

- Any retention, cap, window, dedupe, or prune logic must explicitly distinguish display limits from real storage deletion.
- Any change that can reduce production current totals must show its real-data impact before implementation and obtain explicit user authorization.
- Storage optimization must never be treated as implicit authorization.

### 8.2 部署門禁 / Deployment gates

- 單調校驗必須以真實基線為準，不得用新 cap 掩蓋回退。
- 若 current 降幅超過容差，部署必須失敗，並顯示具體平臺、舊值、新值和差額。
- 任何例外必須是短期、可追蹤、經用戶批准的遷移豁免。

- The monotonic guard must use the real baseline and must not hide regression behind a new cap.
- If current drops beyond tolerance, deployment must fail and show platform, previous value, new value, and delta.
- Any exception must be temporary, traceable, and explicitly approved by the user.

### 8.3 備份與恢復 / Backup and recovery

- 每個備份批次必須包含 manifest、條數、時間、文件大小和 SHA-256。
- 單平臺資產與整包資產必須來自同一批次；不一致則備份任務失敗。
- 恢復前先凍結寫入；恢復後先核對 truth、manifest、debug snapshot，再恢復調度。
- 恢復必須只寫目標平臺，禁止為恢復一個平臺而重寫所有平臺。

- Every backup batch must include a manifest, record count, timestamp, file size, and SHA-256.
- Single-platform assets and bundle assets must come from the same batch; otherwise the backup job must fail.
- Freeze writes before recovery; verify truth, manifest, and debug snapshot before resuming scheduling.
- Recovery must write only the target platform and must never rewrite all platforms to restore one.

## 九、責任結論 / 9. Accountability

本次事故不是用戶操作失誤，也不是數據源自然衰減，而是未經授權的代碼裁剪造成。用戶依靠自己堅持保留 GitHub 完整備份，才避免了不可逆損失。

This incident was not caused by user error or natural source decay. It was caused by unauthorized truncation logic. Irreversible loss was avoided because the user had insisted on retaining a complete GitHub backup.

最終恢復成功不抵消此前的錯誤。正確結論是：生產小紅書 current 已恢復，但開發授權、恢復隔離、備份一致性和單平臺恢復能力仍需繼續硬化。

Successful recovery does not erase the preceding failures. The accurate conclusion is that production Xiaohongshu current has been restored, while development authorization, recovery isolation, backup consistency, and single-platform recovery still require hardening.
